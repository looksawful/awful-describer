# Engineering Audit — 2026-09-09

> Historical snapshot. This document records the audit that led to PR #9. Current implementation status, issue ownership, and verification claims must be checked against the current branch, PR, CI, and GitHub Issues before reuse. In particular, the candidate now has an Electron boot smoke in CI, and residual work extends through #18.

## Scope

Deep audit of Awful Describer covering TypeScript correctness, Electron privilege boundaries, Ollama lifecycle, renderer state/queue behavior, file/preview handling, Windows compatibility, dependencies, testing, CI, repository hygiene, and agent/documentation readiness.

Repository baseline at audit start: one initial commit, no tests, no CI, no README, no issues, mostly TypeScript/TSX with `strict: true`, plus JavaScript Tailwind/PostCSS configuration.

## Executive assessment

The initial `v1.0.0` engineering baseline was not release-grade. The largest risks were unverified build health, duplicated IPC contracts, shell-string process operations, broad Ollama process termination, ineffective cancellation, renderer code that failed strict TypeScript, obsolete Windows probes, and a legacy Electron/dependency tree.

PR #9 now has successful Windows pull-request CI for the current candidate context, including strict TypeScript checks, Node unit tests, production build, and a synthetic Electron boot smoke. That evidence is useful but narrow: it does not prove the real application bootstrap, packaged Windows runtime, filesystem authorization, installer authenticity, or real Ollama inference. Residual work is tracked separately instead of being presented as already solved.

## Findings and disposition

### P0 — Reproducibility and TypeScript baseline

**Finding:** No test script, quality gate, CI workflow, or commit status existed. Strict TypeScript was configured but not demonstrably passing. `KeyboardShortcuts.tsx` referenced a non-existent `selectedImage` store field.

**Action:** Added explicit renderer/main/node/test typechecks, `node:test` unit tests, aggregate `npm run check`, Windows GitHub Actions, and fixes for the strict TypeScript blockers.

**Tracking:** #1 — closed.

### P0 — IPC contract duplication and privileged capability surface

**Finding:** Renderer declarations, preload methods, and main handlers independently described the API. Runtime handler arguments were trusted. Shell/filesystem/process capabilities were broader than necessary.

**Action:** Added `src/shared/ipc.ts` as the shared contract, runtime sanitizers, main-frame sender validation against the trusted renderer URL, deny-by-default navigation/window behavior, permission denial, webview blocking, CSP, a typed preload bridge, exact listener cleanup, and an HTTPS-only external URL policy.

**Residual:** Sender validation does not authorize renderer-provided filesystem paths. #11 owns the main-process grant model. Its registry/design can precede #7; supported drag/drop grant issuance is completed together with #7. Installer authenticity is separately tracked by #12.

**Tracking:** #2 — closed; #11/#12 remain open.

### P0 — Shell/process risk

**Finding:** Model deletion and installer execution used shell-command-oriented paths, and Ollama stop behavior could affect processes not owned by the application.

**Action:** Ollama CLI operations now use executable plus argument arrays with `shell: false`. Normal shutdown tracks/stops only the app-owned Ollama child. Installer launch is restricted to the exact current-session download path.

**Residual:** Current-session path equality is not authenticity verification. #12 owns independent verification and bounded/atomic download hardening.

**Tracking:** #2/#3 — closed; #12 remains open.

### P0 — Cancellation and retry lifecycle

**Finding:** Renderer Stop only set a queue flag while the active HTTP generation continued. Readiness timeout/error paths could create duplicate retry branches.

**Action:** Added request IDs, an active-request registry, request destruction on cancel, duplicate-request protection, one bounded readiness loop, response-size limits, app-owned child cleanup on failed startup, and batch setting snapshots.

**Residual:** `stopOwned()` currently reports whether a kill signal was issued, not confirmed process/server shutdown. Truthful lifecycle completion is tracked by #15.

**Tracking:** #3 — closed; #15 owns the residual UI/runtime-state semantics.

### P1 — Keyboard/queue behavior mismatch

**Finding:** `Ctrl+O` opened a dialog and discarded results. `Ctrl+Enter` depended on missing `selectedImage`. Escape did not cancel the active request.

**Action:** Keyboard shortcuts now reuse real queue state/actions and Escape calls request cancellation.

**Residual:** Queue mutation while a run is active is a separate state-model problem tracked by #14. Shortcut/tool-tip mismatches outside the original #4 scope are grouped in #17.

**Tracking:** #4 — closed; #14/#17 own later residuals.

### P1 — Panel-state contract drift

**Finding:** `panels.presets.visible` was ignored; fixed containers could reserve layout space when panels were hidden.

**Action:** Layout now derives container existence from actual child visibility and honors presets visibility.

**Tracking:** #4 — closed.

### P1 — Preview race, MIME mismatch, and memory amplification

**Finding:** Preview reads could race when selection changed quickly. All previews were labeled PNG regardless of source format. Full base64 data was duplicated in local state and Zustand.

**Action:** Added MIME-aware read results, a latest-operation gate for stale async loads, and removed redundant base64 storage from the image entity.

**Residual:** The normal path still reads source bytes and converts them to base64 on demand. End-to-end memory/resource budgets and read races are tracked by #13; advertised image-format behavior is rechecked under #17.

**Tracking:** #5 — closed; #13/#17 own residuals.

### P1 — Numeric option corruption

**Finding:** Empty/invalid number inputs could create `NaN` and reach state or generation input.

**Action:** UI numeric updates ignore non-finite values and clamp exposed controls. Main-process sanitization rejects non-finite numbers.

**Residual:** Main-side product ranges for supported model options and validation of restored/persisted values are not complete. #13 owns main-side ranges; #6 owns persisted-state validation/migration.

**Tracking:** #6/#13 — open.

### P1 — Obsolete Windows host probing

**Finding:** CPU usage depended on `wmic`, and port probing parsed shell `netstat` output.

**Action:** Replaced both with the already-declared `systeminformation` dependency.

**Tracking:** the probe subtask is complete; #6 remains open for dependency/state/persistence cleanup.

### P0 — Vulnerable/deprecated dependency tree

**Finding:** The first clean Windows CI install reported 32 advisories: 3 low, 3 moderate, 24 high, and 2 critical, plus deprecated transitive packages.

**Action:** Created #10 for reproducible classification and remediation instead of applying `npm audit fix --force` blindly.

**Important:** `32` is historical snapshot evidence, not a permanent project fact. Re-run `npm audit --json` after lockfile changes before making a current security claim.

**Tracking:** #10 — open.

### P1 — Electron runtime line and drag/drop

**Finding:** The candidate still pins Electron 28. Legacy drag/drop uses renderer `File.path`, which is incompatible with the intended supported-runtime migration.

**Action:** #11 defines the filesystem capability model first. #7 then integrates supported drag/drop path acquisition with that model and owns the controlled Electron/electron-builder upgrade plus post-upgrade security/runtime verification.

**Tracking:** #7/#11 — open and coordinated; neither is a duplicate or a simple one-way blocker for the whole of the other.

### P1 — Dead dependencies/state and persistence evolution

**Finding:** `canvas` and `electron-store` appear unused in candidate source. Persisted `autoSave`/`outputDirectory` are not connected coherently to product behavior. Zustand persistence has no explicit version/migration/validation strategy, while history stores absolute paths, prompts, and full results.

**Action:** Removed the unused models-directory scanner during baseline work. Direct-dependency proof/removal and migration-safe persisted-state cleanup remain separate because they affect the lockfile and compatibility surface.

**Tracking:** #6/#10 — open.

### P1 — Filesystem capability ownership

**Finding:** A trusted renderer can still submit arbitrary image-like local paths to privileged file IPC within the OS account's permissions. Extension/size checks are defense in depth, not authorization.

**Action:** #11 defines a main-owned file/directory/derived-result grant registry. Dialog grants can be designed independently; drag/drop issuance is completed during #7 after the legacy `File.path` path is removed.

**Tracking:** #11/#7 — open.

### P1 — Installer authenticity and download lifecycle

**Finding:** The installer flow is HTTPS-only, redirect-bounded, and restricted to the current-session path, but the executable is written to a predictable final path, has no independent maximum byte budget, and is not independently authenticated before launch.

**Action:** #12 owns bounded download, unique `.part` handling, deterministic cleanup, independent publisher/digest verification, atomic finalize, and truthful renderer failure handling.

**Tracking:** #12 — open.

### P1 — Cross-process and long-running resource budgets

**Finding:** Several per-item limits exist, but the complete privileged path has no coherent budget. The shared generation contract accepts up to 16 base64 strings, each capped by JavaScript string length at `70 * 1024 * 1024` characters, while the current UI sends one image. CLI output is retained without a total cap, save content has no explicit maximum, and some file/payload races remain.

**Action:** #13 owns product-justified aggregate/main-side limits and lifecycle ownership. Do not describe the base64 string-length cap as a 70 MiB source-file limit.

**Tracking:** #13 — open.

### P1 — Queue/operation state

**Finding:** Model/prompt/options/preset are snapshotted at batch start, but `pendingImages` remains a captured work list while live UI mutations can remove or clear visible queue items. Progress and visible state can therefore diverge.

**Action:** #14 owns explicit operation identity/state, immutable run snapshot semantics, mutation locks/reconciliation, deterministic cancellation, and queue capacity reporting.

**Tracking:** #14 — open.

### P1 — Ollama/model UI truthfulness

**Finding:** Several renderer lifecycle actions are optimistic: Stop locally invents `{running:false}`, installer launch ignores `{success:false}`, failures are not consistently reported, and installed-model detection uses family-prefix matching rather than exact tags.

**Action:** #15 owns authoritative renderer-visible runtime states, exact model identity, confirmed lifecycle refresh, error handling, and coordination with #12/#14.

**Tracking:** #15 — open.

### P1 — Verification depth

**Finding at audit start:** The repository had zero automated tests.

**Current candidate state:** PR #9 now contains strict TypeScript checks, Node unit tests, a production build, and an Electron boot smoke. The smoke creates a test `BrowserWindow`, installs mocked handlers, loads the built renderer/preload, and checks React mount plus selected bridge functions.

**Residual:** It does not exercise the real `main.ts`, actual handler registration, real sender checks, filesystem grants, installer rejection, packaged executable, or real Ollama inference. #16 owns the verification architecture for those higher layers.

**Tracking:** #16 — open; baseline #1/#8 are closed.

### P2 — Renderer/local-first polish

**Finding:** Clipboard promises, shortcut labels, timestamp/version presentation, remote fonts/CSP split, advertised image formats, and low-risk dead renderer surface need a dedicated cleanup without contaminating P0/P1 security changes.

**Tracking:** #17 — open.

Biome, Knip, and Playwright Electron are **candidates**, not project requirements. Add any of them only when evaluation shows a useful, low-noise role and the repository gains an explicit script/config/CI owner. Strict `tsc` remains the type authority.

## Release-confidence rule

Do not call the repository release-ready from a green typecheck, unit suite, build, or existing boot smoke alone. The required evidence must match the claim being made. At minimum for release-runtime confidence after the current hardening program:

1. clean Windows install from the committed lockfile and fresh dependency classification;
2. strict type/unit gates and production build;
3. existing renderer/preload boot smoke;
4. real application bootstrap/main-process smoke;
5. packaged Windows smoke;
6. separate real Ollama vision acceptance for supported runtime behavior;
7. critical/high dependency disposition appropriate to exposure;
8. documented supported Electron state, explicit filesystem grants, bounded privileged resources, and installer authenticity.

GitHub Issues remain the canonical implementation backlog. This document remains a historical audit narrative and must not be used to override newer code, PR state, CI evidence, or issue decisions.
